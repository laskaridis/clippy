## Codebase Patterns
- Use `make help` as the canonical discovery surface before adding or invoking repository workflow commands.
- For sandbox image work, keep the Docker build context minimal by copying only `.tool-versions` and late-stage sandbox scripts instead of the full repository tree.
- Sandbox bootstrap should authenticate both `gh` and `git clone` from `GH_TOKEN`; for local-path validation overrides, mark the source repo as a git `safe.directory` before cloning.
- Only forward `SANDBOX_REPO_BRANCH` into the sandbox when that branch exists on `origin`; local-only feature branches will break first-boot checkout.
- Host bind mounts used for sandbox export directories may reject `chown` on this Docker stack, so bootstrap must warn and continue instead of treating ownership changes as fatal.
- For sandbox web access, keep the published backend port identical inside and outside the container, then export `DJANGO_DEV_PORT` and `DJANGO_DEV_BASE_URL` from the entrypoint so host browser URLs and extension runtime metadata stay aligned.
- Sandbox documentation should describe the deterministic id-to-resource mapping and recovery semantics exactly as implemented in `Makefile`, because users rely on the printed SSH/web/export values instead of discovering container internals manually.
